# roux 0.2.0: forms that are easy to write

Status: draft for review. Builds on [the roux design](2026-11-14-roux-design.md) (decisions 11 and 12).

## Why

Building a Customers page by hand on roux 0.1.0 (the template's `customers-trial` branch) worked, but
the form took about 110 lines for four fields, and most of them were plumbing every form repeats:
dialog open state, validators on each field, `send`, `showProblem`, cache refreshes, retyped
messages. cable-spa (callibrity/cable-spa) does the same by hand with Zod, a `useCreateX` hook file
per endpoint, and `mutateAsync().then().catch()` in every modal: about 130 lines for three fields.

roux's job is to make the right way the easy way. For forms, that means: a Zod schema says what is
valid, a mutation says what the endpoint does, and the form says only what is on screen.

## Goals

- A typical create/edit form is about 20 lines: defaults, a success message, the fields.
- One way to submit, shared by forms and buttons: a TanStack Query mutation declared once per
  endpoint, with what it refreshes.
- Browser messages are the server's messages, without retyping them.
- Nothing a new app has to know to stay out of trouble (the CSP clash with Zod).
- The pieces apps still copy from the template move into roux.

## Non-goals

- The generator that writes schemas and mutations from Java records (stage 2 proper). 0.2.0 makes
  what it will write short; it does not write it.
- Replacing TanStack Form. `useAppForm` stays available for unusual forms.
- CSV export (still the template's).

## Decisions

### 1. Zod is a peer dependency of `@jwcarman/roux-web`

`/form` imports Zod and calls `z.config({ jitless: true })` when it loads. Zod otherwise probes
`eval` to speed up object parsing, and a Content-Security-Policy without `unsafe-eval` (the
template's) records a violation on every page. Found by the template's Playwright CSP tests.

### 2. Rule helpers carry roux's wording (`/form`)

```ts
text()            // string, trimmed, required: "Must not be blank"          (@NotBlank)
text().optional() // string, trimmed; "" becomes null
text().max(100)   // "Must be between 0 and 100 characters"                  (@Size)
email()           // required, trimmed: "Must be a valid email address"      (@Email)
url(), phone(), date(), number(), integer()
oneOf(VALUES)     // an enum: "Must not be empty" when unset                 (@NotNull enum)
```

The messages are the ones in `ContributorValidationMessages.properties`, so a field shows the same
words whether the browser or the server caught the mistake. The list started from cable-spa's
`src/lib/schemas/common.ts`. Messages do not repeat the field's name: they sit under its label.

### 3. Each resource has a typed API module, on roux's fetch client

Taken from cable-spa's `src/lib/api` (`ClientsApi`): one typed function per endpoint, so queries,
mutations, loaders and tests share one place per URL. Plain functions, not classes; no axios.

```ts
export const customersApi = {
  list: (params: CustomerListParams, signal?: AbortSignal) =>
    getJson<PageDto<Customer>>("customers", { params, signal }),
  get: (id: string, signal?: AbortSignal) => getJson<CustomerDetail>(path`customers/${id}`, { signal }),
  create: (request: CustomerRequest) => sendJson<CustomerDetail>("POST", "customers", request),
  update: (id: string, request: CustomerRequest & { version: number }) =>
    sendJson<CustomerDetail>("PUT", path`customers/${id}`, request),
};
```

roux stays on `fetch` (it already does CSRF, session loss and Problem Details; axios would add a
dependency and a second error type). The client gains:

- `sendJson<T>(method, path, body)`: the write-side partner of `getJson`.
- `baseUrl` in `configureApi` (default `/api`), so modules write `customers`. A path without a leading
  slash goes under `baseUrl`; one with a leading slash (`/who/me`) is used as it is.
- `{ params }` on `getJson`: a query string from an object, leaving out `undefined` and repeating a
  key for an array.
- `{ signal }` on `getJson`, so TanStack Query can cancel a request no one needs (a superseded search).
- `PATCH` in `send`.
- `` path`customers/${id}` ``: a tagged template that encodes every value it inserts.
- An `upload()` with progress, on `XMLHttpRequest`, only when an app needs it (not in 0.2.0).

The generator (stage 2) writes the module from the controller, one function per method.

### 4. Mutations are declared once per endpoint, with `mutationOptions`

```ts
export const updateCustomer = (id: string, version: number) =>
  mutationOptions({
    mutationFn: (request: CustomerRequest) => customersApi.update(id, { ...request, version }),
    meta: { refreshes: [queryKeys.customers.detail(id), queryKeys.customers.lists()] },
  });
```

- `meta.refreshes` is honoured by roux's query client (decision 8) after every answer, success or
  refusal: a refusal (a 409, say) usually means the page is out of date.
- A resource's API module, queries (`customerQuery(id)`) and mutations live together in one file.

### 5. `useSchemaForm` (`/form`)

```tsx
const form = useSchemaForm({
  schema: customerRequestSchema,
  defaultValues: customer ?? { name: "", email: "", company: "", status: "LEAD" },
  mutation: customer ? updateCustomer(customer.id, customer.version) : createCustomer,
  onSuccess: (saved) => notify.success(`${saved.name} was saved`),
  failure: "Could not save the customer", // optional; the default is "Could not save"
});
```

- Validates with `schema` on blur and on submit (form-level, so `.refine()` cross-field rules land on
  the field their path names).
- Submits the schema's parsed output (trimmed, `""` to `null`, coerced), typed as that output, through
  the mutation.
- A 400 with `errors[]` puts each message on its field (today's `showServerErrors`); one naming no
  field shown is a toast. Any other refusal is a toast titled `failure` with the server's `detail`
  underneath (today the detail replaces the title).
- `onSuccess` gets the parsed response.
- Returns an ordinary `useAppForm` form, so `FormDialog`, the fields, `SubmitButton` and
  `SubmittingIndicator` work unchanged; the form's `isSubmitting` covers the mutation.

`useServerAction` takes a mutation in the same way (`useServerAction(archiveCustomer(id))`) and keeps
its toast-on-refusal behaviour, so buttons and forms share one core.

### 6. Fields read the schema

- `required` comes from the schema (no `.optional()`), so the asterisk needs no prop.
- `maxLength` comes from `.max(n)`.
- `SelectField` takes `options` as values (`CUSTOMER_STATUSES`) with an optional `labels` map, or as
  `{ value, label }` pairs whose value may be a number or boolean (cable-spa's payment terms); the
  field converts the `<select>`'s string back to the value's type.

### 7. Forms in a dialog and forms on a page

**In a dialog**, `FormDialog` manages its own open state: once the dialog has closed the form resets
to its defaults (so it opens on them), and a successful submit closes it after `onSuccess`. Passing `open` and `onOpenChange` keeps today's
controlled behaviour, for a page that opens it from code. `submitLabel` defaults to "Save".

**On a page**, the same `useSchemaForm` goes in `<form.Form>` with `<form.SubmitButton>` (and,
optionally, `<form.ResetButton>`). After a successful submit the form stays, and its defaults become
the saved values: it is no longer dirty, Reset goes back to what was saved, and the next submit
sends the new version. `onSuccess` may navigate instead (a create page going to the new record).

```tsx
<form.Form>
  <form.AppField name="appName">{(f) => <f.InputField label="App name" />}</form.AppField>
  …
  <form.SubmitButton>Save</form.SubmitButton>
  <form.ResetButton />
</form.Form>
```

The template's Appearance page moves onto it as the proof.

### 8. roux provides the query client (`/api`)

`createQueryClient()` moves from the template: no retries for a 4xx, two for anything else, plus the
mutation cache hook that honours `meta.refreshes`. `useClearQueriesOnIdentityChange` moves with it.

### 9. The rest of the template's shared pieces move

| From the template | To |
|---|---|
| `SearchInput`, `DebouncedSearchInput` | `/table` (beside `useDebounce`, `FilterChips`) |
| `InfiniteList`, `InfiniteSelect` | `/paging` |
| `NotFoundPage`, `ErrorPage`, `removal` | `/feedback` |
| `queryClient.ts` | `/api` (decision 8) |

`ActivityList` and `relativeTime` (the template's activity feature) and `ExportButton` (CSV) stay.

### 10. The old ways go (0.x allows breaking changes)

0.2.0 removes what the new pieces replace, and the template moves in the same release:

- `showProblem` and `showServerErrors` (`useSchemaForm` handles refusals).
- `useServerAction`'s options shape (`request`, `failure`, `refreshes`): it takes a mutation.
- `textOrNull`, `numberOrNull`, `instantOrNull` (the schema's parse does this).

## The Customers form, after

```tsx
export function CustomerFormDialog({ customer, trigger }: { customer?: CustomerDetail; trigger: ReactElement }) {
  const form = useSchemaForm({
    schema: customerRequestSchema,
    defaultValues: customer ?? { name: "", email: "", company: "", status: "LEAD" },
    mutation: customer ? updateCustomer(customer.id, customer.version) : createCustomer,
    onSuccess: (saved) => notify.success(`${saved.name} was saved`),
  });

  return (
    <FormDialog form={form} title={customer ? `Edit ${customer.name}` : "New customer"} trigger={trigger}>
      <form.AppField name="name">{(f) => <f.InputField label="Name" />}</form.AppField>
      <form.AppField name="email">{(f) => <f.InputField label="Email" type="email" />}</form.AppField>
      <form.AppField name="company">{(f) => <f.InputField label="Company" />}</form.AppField>
      <form.AppField name="status">{(f) => <f.SelectField label="Status" options={CUSTOMER_STATUSES} />}</form.AppField>
    </FormDialog>
  );
}
```

## Proof

- The template moves to 0.2.0: its invite form, the Customers form (dialogs) and Appearance (a page
  form) use `useSchemaForm`, its buttons use mutations, the moved components are deleted, and the full build (Java, Vitest, Playwright including the CSP tests) passes.
- roux-web keeps 100% coverage and a 100% Stryker score.
- A contract test checks that each rule helper's message equals the server's message for the same
  constraint (read from `ContributorValidationMessages.properties`).

## Not in this release

- A Java helper for one-value list filters (`statusIs(...)` specifications written by hand in each
  service): a better fit for jpa-utils, beside its search support, later.
