# Dojo Round 3: Memberships, Payments and Money Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** roux gains money (a Java value, its wire shape, validation, a form rule and field, display), and the dojo uses it for plans, memberships, payments, overdue students and monthly totals.

**Architecture:** A new `runtime/roux-money` module (in the starter) holds `Money`, its constraints and `GET /api/money`; roux-web gains a `/money` entry (type, format, currency query) and a `money()` rule plus `MoneyField` in `/form`, kept identical to the server by `contracts/money.json`. The dojo adds a `plans` and a `memberships` package; paid through is computed (a SQL view for the list, the same arithmetic in Java for a student's page), never stored.

**Tech Stack:** Spring Boot 4.1.3, Java 25, Hibernate 7, PostgreSQL 16, Liquibase; React, Chakra UI v3, TanStack Query/Form/Table, Zod, Vitest + MSW, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-20-dojo-round-3-memberships-design.md`

## Global Constraints

- No warning suppression of any kind; no star imports (Java, TS, build selectors).
- Every roux module: 100% line and branch coverage from its own tests (JaCoCo); spotless per module (`./mvnw -q -pl <module> spotless:apply`).
- Money is never a floating-point number: `long` minor units in Java and SQL (`bigint`), integers in JSON and TypeScript.
- JSON shape: `{ "minorUnits": 15000, "currency": "USD" }`; `GET /api/money` → `{ "currency": "USD", "fractionDigits": 2 }`.
- Columns: `<name>_minor_units bigint not null`, `<name>_currency char(3) not null`.
- Messages (both sides, identical): `Must be more than 0`, `Must not be negative`, `Must be in USD` (the configured code), `Must be an amount`, `Must have at most 2 decimal places` (n from the currency; for 0 digits: `Must be a whole amount`).
- Refusals are Problem Details: `NotFoundException`, `InvariantViolationException`, `InvalidFieldException`; edited records carry `version` (409 when stale); time from the injected `Clock`; mutations name `meta.refreshes`; icons from `react-icons/lu`.
- Liquibase: new changesets only, never edit one that has run.
- Permissions: `plans.manage` (OWNER), `payments.record` (OWNER, INSTRUCTOR), `payments.read` (OWNER); constants in the dojo's `identity/Permissions`, granted in a new changeset `dojo-roles-2` in `roles.xml`; `permissions.gen.ts` regenerated by `PermissionsTest`.
- Paid through = start + (periods paid) months (MONTHLY) or years (YEARLY) − 1 day; Java `plusMonths/plusYears` and PostgreSQL `+ interval` must agree.
- Overdue = student ACTIVE, has a current membership, paid through < today (`LocalDate.now(clock)`).
- Commits straight to main, never pushed without the user's OK; trailer:

## Review Focus

1. **Month-end starts.** A monthly membership starting Jan 31 with 1 period: Java and the view must both say Feb 27 (Jan 31 + 1 month = Feb 28, − 1 day); with 2 periods, Mar 30. (Task 4 test `paidThroughAgreesWithTheViewAtMonthEnd`.)
2. **Typed amounts.** `1,000.50`, `$150`, `150.`, `.5`, ` 150 `, `-5`, `1e3`, `150.555`, and for JPY `150.5`: each parses or refuses exactly as `contracts/money.json` says. (Task 2 fixture cases.)
3. **Payment with no membership.** Recording a payment for a student with no current membership is a 400 `InvariantViolationException` "Start a membership first", not a 500. (Task 4 test.)
4. **A member's view of the student list.** A MEMBER's `GET /api/students` rows carry null `planName`, `paidThrough`, `payment`; `?payment=OVERDUE` and `?sort=PAID_THROUGH` are 403. (Task 5 tests.)
5. **Plan change before the current one starts.** Starting a membership on or before the current one's start date is a 400 on `startDate` "Must be after the current membership's start (2026-03-15)"; the earlier-than-paid-through warning appears in the dialog only. (Task 4 and Task 8 tests.)
