# Dojo round 1: ranks, students, promotions, the Instructor role

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (chosen: built inline in
> one session, the user is watching the token budget) to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking. One review at the end, on Sonnet.

**Goal:** The dojo's first school features, built the way the roux skill says, with every workaround
logged in `examples/dojo/FINDINGS.md` and the small general ones fixed in roux.

**Architecture:** Two new feature packages beside `members` (Java `ranks`, `students`; frontend
`src/ranks/`, `src/students/`), each a JPA entity + repository + service + controller, Liquibase
changelog, a roux-web API module, pages and dialogs. A promotion is a child of a student; the current
rank is computed from the latest promotion.

**Tech Stack:** As the dojo: Spring Boot 4.1, roux-problems/roux-autoconfigure, who 0.20 RBAC,
jpa-utils paging, PostgreSQL/Liquibase; React 19, Chakra v3, TanStack Router/Query/Form/Table,
`@jwcarman/roux-web` (`useSchemaForm`, `QueryTable`, `notify`, `useConfirm`), Vitest + MSW,
Playwright.

**Spec:** `docs/superpowers/specs/2026-11-17-dojo-example-design.md`, "Round 1: students and ranks",
"The findings log", "Building with the plugin", "Round 1 is done when".

## Global Constraints

- The roux skill (`plugins/roux/skills/roux/SKILL.md`) is followed as written: read the guide it
  routes to before writing code. Where it is wrong or silent, that is a finding.
- Only roux's public API (Java packages roux documents, the six `@jwcarman/roux-web` entry points).
- Records over the wire: `Rank`, `RankRequest`, `Student`, `StudentDetail`, `StudentRequest`,
  `Promotion`, `PromotionRequest`, `PageDto<Student>`. Requests that edit carry `Long version`.
- Refusals are exceptions (`InvalidFieldException`, `InvariantViolationException`, a
  `NotFoundException` subclass per resource); no `@ExceptionHandler`, no `ResponseEntity` errors.
- Field rules are Bean Validation on the request record; the browser's rules come from roux's rule
  helpers with the same limits.
- Never suppress warnings; no star imports; Spotless clean.
- No who client changes this round (waits for who's API-surface release).
- A roux fix lands as its own commit with roux's bars (100% coverage, 100% Stryker on roux-web) before
  the dojo commit that uses it; anything bigger is a deferred finding for the user.
- Commits straight to main; push after the final review.

## Review Focus

1. Two students promoted on the same day to different ranks / a promotion back-dated before an
   existing one: the current rank is the promotion with the latest date (ties: latest created).
2. Removing a rank a student holds or has held → 409 with the reason; the rank stays.
3. Reordering at the ends (move up the first, move down the last) is refused or a no-op, never a
   gap or duplicate position; positions stay 1..n after a removal.
4. Rank name uniqueness ignores case and surrounding spaces ("Black Belt" vs " black belt").
5. Deep links `/ranks`, `/students`, `/students/<id>` reload signed out → the shell, not 401.

### Task 1: Ranks

**Files:** Create `src/main/java/.../dojo/ranks/{Rank entity RankEntity, RankRepository, RankService,
RanksController, RankNotFoundException}.java`, `src/main/resources/db/changelog/ranks.xml` (include in
master), `frontend/src/ranks/{ranks.ts, RanksPage.tsx, RankDialog.tsx}`, route
`frontend/src/routes/_signedIn/ranks.tsx`, nav entry; tests beside each. Modify `AppRoles`
(`RANKS_READ = "ranks.read"`, `RANKS_MANAGE = "ranks.manage"`; OWNER both, MEMBER read),
`SpaController.ROUTES` and `who.security.public-paths` (`/ranks`).

**Interfaces — Produces:** `GET /api/ranks` → `List<Rank>` ordered by position (a short list, fetched
whole); `POST /api/ranks` (`RankRequest(name, colour)`) → `Rank`; `PUT /api/ranks/{id}`
(`RankRequest(name, colour, version)`); `POST /api/ranks/{id}/move-up`, `/move-down`;
`DELETE /api/ranks/{id}`. `Rank(UUID id, String name, BeltColour colour, int position, long version)` (a `BeltColour` enum, as the forms guide has it).
Name: required, ≤ 40, unique ignoring case and trim (`InvalidFieldException("name", "A rank already
has that name")`). Colour: required, one of `BeltColour`. Removal of a rank in any promotion → 409
`InvariantViolationException("Students hold or have held this rank")` (Task 3 adds the check; until
then removal always succeeds).

- [ ] Java tests (`@AppTest`, `TestMembers`): create/list order; duplicate name (case/space variants)
  → 400 on `name`; > 40 → 400; bad colour → 400; move-up first / move-down last → 409 "Already
  first"/"Already last"; remove renumbers 1..n; stale version → 409; MEMBER can list, gets 403 on
  every write; signed-out deep link `/ranks` serves the shell (SpaRoutingTest picks it up from ROUTES).
- [ ] Implement until green.
- [ ] Vitest + MSW: page lists ranks with swatch; add/rename dialog shows server field error under
  Name; move buttons disabled at the ends; remove asks first (`useConfirm`).
- [ ] Implement page, dialog, API module; `npm test` green.
- [ ] Log findings met; commit `feat(examples): the dojo's ranks`.
