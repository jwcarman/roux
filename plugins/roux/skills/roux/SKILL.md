# roux

roux is the base of a Go + React 19 app: Go packages for what an app never changes (sign-in,
roles and permissions, the team, Problem Details errors, paging, money, dates, the activity log)
and plain app code for what it does (tables, services, handlers, pages). There is one way to do
each thing. The SPA and the API share one origin, served by one Go binary.

This skill assumes the app was generated by `create-roux-app` (roux's template): `cmd/server` with
`modules.go` and `permissions_test.go`, `internal/<feature>/` packages, golangci-lint, and a
frontend with a 100% Vitest coverage gate. Its check script and the recipe rely on them.

roux's names are its own (`k.Handle`, `problem.InvalidField`, `page.New`, `sendJson`,
`meta.refreshes`, `useSchemaForm`, `QueryTable`): guesses from general Go or React knowledge are
wrong in the details. **Read the reference for the task before writing code, and take names from
it.** Each reference is rules, exact names, steps, an example, the check and the pitfalls.

## First, look at the project

- **Versions:** this skill covers roux **0.4.0**, the Go server. `github.com/jwcarman/roux` in
  `go.mod` and `@jwcarman/roux-web` in `frontend/package.json` must be that or newer; roux 0.3.0
  and earlier were Spring Boot. If not, tell the user before anything else.
- **The nearest feature:** in a grown app, find the existing feature most like the task and copy its
  shape (package, files, imports, tests). Go is packaged by feature (`internal/<feature>/`), the
  frontend foldered by feature (`frontend/src/<feature>/`); route files under `src/routes/` stay
  thin. A file holding one component is PascalCase (`LabelsPage.tsx`); a module of several things is
  camelCase (`labels.ts`); a test is named after its file.
- **What is shared:** `cmd/server/modules.go` (the modules and `permissions()`),
  `cmd/server/migrations/` (the app's roles), `src/queryKeys.ts`, `main.tsx`, `src/shell/nav.ts`,
  `src/testing/`, the app's `CLAUDE.md`. One Go module per app.

## The conventions

- A feature is a Go package with its SQL migrations embedded; SQL text is constant and values are
  `$n` arguments, so nothing a request sends becomes SQL.
- Handlers take a body struct and answer a JSON struct carrying `version`; an edit sends the
  `version` it read, which is how a stale save becomes a 409.
- Refusals are `*problem.Problem` values returned as the error (`problem.NotFound`,
  `problem.Validation`, `problem.InvalidField`, `problem.Conflict`, `problem.StaleVersion`). Never
  write an error response yourself: roux makes the Problem Details the browser reads. Messages are
  for people.
- Every route is `k.Handle(pattern, permission, fn)`, a permission, never a role: roles are data the
  owner edits. Permissions are granted in the feature's migration, by role name.
- One frontend module per resource: schema, API object (`getJson`, `sendJson`, `path`), queries,
  mutations. Pages never call the API or `fetch` (the module adds CSRF and reads problems).
- Mutations name what they refresh in `meta.refreshes`, never `invalidateQueries`; use
  `createQueryClient()` (`testQueryClient()` in tests), never `new QueryClient()`: only roux's client
  runs the refreshes, and forms wait for them.
- Forms go through `useSchemaForm` with roux's rule helpers (`text()`, `oneOf()`...); never retype a
  server message: the helpers and `validate` share roux's words, so the two never disagree.
- Buttons that change data use `useServerAction`; consequences ask first with `useConfirm`; outcomes
  are told with `notify`.
- Long lists are paged by the server (`page.New`) and shown with `QueryTable`, state in the URL (so
  a link or reload keeps the page).
- Import roux-web only from its subpaths (`@jwcarman/roux-web/api`, `/form`, `/table`...): it has
  no root export.
- Time from the module's clock, today from the organization's zone, so tests set the time and
  "today" is the organization's, not the server's.
- Never suppress a warning (no `//nolint`, no `eslint-disable`); no star imports.

## Before you finish

From the app's root, **run** `bash <this skill's base directory>/scripts/check.sh`. In the order the
build needs, it formats the Go (`gofmt -w`), rewrites `permissions.gen.ts` through the permissions
test, runs `go vet` and golangci-lint, the Go tests when a database is reachable
(`TEST_DATABASE_URL`, or Docker), then the frontend's tests with the 100% coverage gate and its
type-checked build. It stops at the first failure with what to fix. Fix it and run it again until it
ends `check: ok`.

It names each step it skipped. When it skipped the Go tests, tell the user, and read your Go tests
against `feature.md` step 7: role names exist, `a.Role` comes before `a.Migrate`, and every request
body satisfies `validate` except in the test of that rule.

Then check the change against the **Pitfalls** of each reference you used. A test that fails is a
finding to fix, not to delete. If no reference covers what the task needs, say so to the user
rather than inventing an API.
