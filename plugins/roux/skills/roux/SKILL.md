# roux

**An app's feature screens are surfaces**: A2UI JSON drawn from roux's catalog
(`<id>.surface.json`), its generated types (`<id>.surface.gen.ts`) and a binding
(`<id>.binding.ts`) over the feature's `cqrs` queries and commands. React is written only for
catalog primitives (in roux-web) and roux's built-in pages. A screen the catalog can't draw needs
a new primitive, never a hand-written screen (the surfaces reference, below).

roux is the base of a Go + React 19 app: Go packages for what an app never changes (sign-in,
roles and permissions, the team, Problem Details errors, paging, money, dates, the activity log)
and plain app code for what it does (tables, domain services, queries and commands, surfaces).
There is one way to do each thing. The SPA and the API share one origin, served by one Go binary.

This skill assumes the app was generated by `create-roux-app` (roux's template): `cmd/server` with
`modules.go` and `permissions_test.go`, `internal/<feature>/` packages, golangci-lint, and a
frontend with a 100% Vitest coverage gate. Its check script and the recipe rely on them.

roux's names are its own (`cqrs.Command`, `problem.InvalidField`, `page.New`, `bind`,
`Surface`, `roux-surface-types`): guesses from general Go or React knowledge are
wrong in the details. **Read the reference for the task before writing code, and take names from
it.** Each reference is rules, exact names, steps, an example, the check and the pitfalls. The
references name every export (a script checks it), so there is no need to read
roux's source or `node_modules` to confirm one: write the code, and the build and the check script
name anything wrong. The TypeScript language server may not start (TypeScript 7 has no
`tsserver`): search the code, and `npm run build` is the type check.

## First, look at the project

- **Versions:** this skill covers roux **0.6.1**, the Go server. `github.com/jwcarman/roux` in
  `go.mod` and `@jwcarman/roux-web` in `frontend/package.json` must be that or newer; roux 0.3.0
  and earlier were Spring Boot. If not, tell the user before anything else.
- **The nearest feature:** in a grown app, find the existing feature most like the task and copy its
  shape (package, files, imports, tests). Go is packaged by feature (`internal/<feature>/`), the
  frontend foldered by feature (`frontend/src/<feature>/`); route files under `src/routes/` stay
  thin. A file holding one component is PascalCase (`LabelsPage.tsx`); a module of several things is
  camelCase (`labels.ts`); a test is named after its file.
- **What is shared:** `cmd/server/modules.go` (the modules and `permissions()`),
  `cmd/server/migrations/` (the app's roles), `src/queryKeys.ts`, `main.tsx`, `src/shell/nav.ts`,
  `src/testing/`, the app's `CLAUDE.md`. One Go module per app.

## The conventions

- A feature is a Go package with its SQL migrations embedded; SQL text is constant and values are
  `$n` arguments, so nothing a request sends becomes SQL.
- A feature's reads and changes are its ports: `cqrs.Query` (paged), `cqrs.Lookup` (one value),
  `cqrs.Command` (a change), served by `cqrs.Mount`. A command's input `Validate`s itself; its
  `Run` is thin and calls the feature's domain service, where the rules live. `Run` gets the
  `pgx.Tx` the command log shares; `cqrs.Module{}` is on before the first feature with commands.
- Refusals are `*problem.Problem` values returned as the error (`problem.Validation`,
  `problem.InvalidField`, `problem.NotFound`, `problem.Conflict`, `problem.StaleVersion`). Never
  write an error response yourself. Messages are for people, in roux's words.
- Every endpoint has a permission, never a role: roles are data the owner edits. Permissions are
  granted in the feature's migration, by role name.
- Generated files are never edited: `permissions.gen.ts` and `contract.gen.ts` (rewritten by
  `go test ./cmd/server`, run twice), `*.surface.gen.ts` (`npm run surfaces`), `routeTree.gen.ts`.
- A screen's binding is a module-level constant; a route renders `<Surface surface={json}
  binding={binding} />` behind `requirePermission`.
- Lists are paged by the server (`page.New`, `Paging: list.Config()`), drawn as a `DataTable` whose
  page, sort and filters are paths the binding reads.
- Import roux-web only from its subpaths (`@jwcarman/roux-web/surface`, `/session`...): it has no
  root export.
- Time from the module's clock, today from the organization's zone, so tests set the time and
  "today" is the organization's, not the server's.
- Never suppress a warning (no `//nolint`, no `eslint-disable`); no star imports.

## Before you finish

From the app's root, **run** `bash <this skill's base directory>/scripts/check.sh`. In the order the
build needs, it formats the Go (`gofmt -w`), rewrites `permissions.gen.ts` through the permissions
test and `contract.gen.ts` through the contract test, runs `go vet` and golangci-lint, the Go tests
when a database is reachable (`TEST_DATABASE_URL`, or Docker), then the frontend: Prettier, the
surfaces' types, its tests with the 100% coverage gate, its type-checked build and ESLint. It stops at the first failure with what to fix. Fix it and run it again until it
ends `check: ok`.

It names each step it skipped. When it skipped the Go tests, tell the user, and read your Go tests
against `feature.md` step 5: role names exist, `a.Role` comes before `a.Migrate`, and every request
body satisfies the input's `Validate` except in the test of that rule.

Then check the change against the **Pitfalls** of each reference you used. A test that fails is a
finding to fix, not to delete. If no reference covers what the task needs, say so to the user
rather than inventing an API.
